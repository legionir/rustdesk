# Protocol inventory: relevant subset

Desktop schema is protobuf3 `libs/base/protos/message.proto`; rendezvous schema is `libs/hbb_common/protos/rendezvous.proto`. `base/build.rs` and `hbb_common/build.rs` generate Rust types. All fields and tags below are in the pinned schema. This is a prioritized subset, not an exhaustive handler/direction analysis. Peers exchange serialized `Message` oneof envelopes; nested `Misc` wraps display/control messages. Actual delivery, authorization and encryption depend on connection state and transport.

| Message and tags | Important fields | Observed handler/direction |
|---|---|---|
| `Message.video_frame=6`; `VideoFrame` | oneof VP9=6, RGB=7, YUV=8, H264=10, H265=11, VP8=12, AV1=13; `display=14`. Encoded entries: `data=1`, `key=2`, `pts=3` | Host `video_service::handle_one_frame` → viewer `client/io_loop.rs::handle_msg_from_peer` → decode thread. |
| `Message.mouse_event=10`; `MouseEvent` | `mask=1`, signed `x=2`, `y=3`, modifiers=4 | Viewer `client::send_mouse` → host `Connection::on_message` → input thread; desktop checks keyboard permission. |
| `Message.key_event=15`; `KeyEvent` | down=1, press=2, oneof control_key=3/chr=4/unicode=5/seq=6/win2win_hotkey=7, modifiers=8, mode=9 | Viewer input → host `Connection::on_message` → input thread. iOS ignores this branch; Android and desktop differ. |
| `Message.login_request=7`, `login_response=8`, `hash=9`, `auth_2fa=27` | `LoginRequest` has username, password bytes, peer identity, options, session_id and optional transfer/forward/camera/terminal scopes. `Hash` has salt/challenge; `LoginResponse` has error or `PeerInfo`. | Host `Connection::on_message`; viewer `handle_msg_from_peer` and `client::handle_hash`. Full handshake, trust and replay guarantees remain unaudited. |
| `PeerInfo`, `DisplayInfo` | displays, current display, platform, encoding, resolutions; display x/y/width/height/name/online/scale | Delivered in login response; viewer handles peer info. Dynamic display handlers need full mapping. |
| `Message.misc=19`: `SwitchDisplay=5`, `CaptureDisplays=30`, `change_display_resolution=36`, `refresh_video_display=31` | display selection, add/sub/set and resolution | Host `Connection::on_message` / `handle_switch_display`, viewer `client/io_loop.rs` handles `SwitchDisplay`. Do not assume all display messages are one-directional; audit each call site. |
| `Misc.permission_info=6`, `option=7` | `PermissionInfo` has Keyboard, Clipboard, Audio, File, Restart, Recording, BlockInput, PrivacyMode; `OptionMessage` includes supported decoding, FPS, disable_keyboard and excluded features | Permission dispatch and update involve connection manager; no separate mouse enum. |
| `Message.test_delay=5` | time, from_client, last_delay, target_bitrate | Host `Connection::start` timer emits; host `on_message` and `client::handle_test_delay` respond. This is application-level delay/liveness logic, not proof of WebSocket ping/pong policy. |
| `Message.public_key=4`, `signed_id=3` | public key exchange values and version; signed identity bytes | Handshake and identity binding must be traced through `tcp` and client/server setup before making security claims. |

Compatibility constraints: protobuf field numbers and nested oneof variants, accepted unknown fields, codec negotiation and the enclosing transport/encryption must be considered together. Some `Misc` fields retain deprecated tags for older peers. The proposed RemoteCore protocol has **not** been selected. No browser interoperability, replay resistance or validation bounds have been established by this inventory.
