# Cloudflare integration — unverified

`libs/hbb_common/src/websocket.rs` implements a client `WsFramedStream`, binary send/receive, timeouts and frame/message bounds (default caps 16 MiB and 64 MiB), TLS and proxy paths; `check_ws` maps server ports to `/ws/id` or `/ws/relay`. `WsFramedStream::set_max_packet_length` clamps both caps. TLS has an explicit invalid-certificate option; whether and how it is enabled requires security review. This does not establish a complete generic WS server, application heartbeat, end-to-end backpressure or a Cloudflare-compatible relay.

A Worker would route transport only; no capture/codec/input in it. Pairing, identity/authorization, TLS termination and end-to-end encryption need a documented threat model. Cloudflare documentation, plan-specific limits and a deployed long-duration test were not available/verified in this environment. Outbound TCP policy, target restrictions, idle behavior, CPU/memory/connections, Durable Objects necessity, pricing and operational viability are **unknown**; none is claimed supported. Consult current official documentation and run real tests before deciding. Core must remain transport-replaceable if Cloudflare proves unsuitable.
